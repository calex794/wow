# WOW/W4 — долговечные разрешения для параллельных копий письма (EXP-013)

Продолжает [LABO-ROUTE-001](https://app.notion.com/p/40032a84beec81768202c3faf8054e83),
[EXP-012](https://github.com/calex794/labo/pull/16) и существующую криптографию W3/W4 репозитория WOW.

## Что фактически реализовано

- Один локальный отправитель контролирует общий лимит **K=1..8 копий** одного письма,
  включая оригинал. Три маршрута (прогноз / разведка / добровольный шлюз) расходуют
  **одну общую** квоту, а не получают отдельный лимит каждый.
- Каждое разрешение на дополнительную копию записывается в **SQLite WAL + synchronous=FULL**
  транзакцией BEGIN IMMEDIATE **до начала передачи**. После потери ответа или
  перезапуска тот же 16-байтовый request ID выдаёт строго тот же slot + псевдоним;
  повтор с другим peer, lane или ciphertext отклоняется.
- Нет автоматического возврата квоты по тайм-ауту: после разрыва нельзя исключить,
  что копию получил офлайновый сосед. Это безопасная в плане переполнения, но
  потенциально недоставляющая политика.
- 128-битные локальная метка и псевдонимы попыток получаются из OS RNG,
  **не вычисляются из публичного ключа получателя**. Это НЕ анонимность:
  пересылки исходно одинакового ciphertext можно коррелировать по байтам и времени.
- Только существующая **Ed25519 W4-квитанция**, верифицированная по текущей записи
  TrustRegistry и BLAKE3 хешу исходного W3 ciphertext, переводит письмо в Recipient.
  Статус и остановка выдачи новых копий фиксируются **одной SQLite транзакцией**.
  Утверждение шлюза/почтового ящика не останавливает поиск получателя.
- В эксперименте повторно используется настоящая существующая цепочка
  W3 signed+HPKE/COSE (закреплённая библиотека Blue) и
  W4 accept_authenticated_and_queue_receipt: два дубликата подавляются после
  рестарта, повторное предъявление возвращает прежние точные байты квитанции.

## Доказательства и ограничения

Пять независимых регрессионных сценариев: K4 при 3 маршрутах и аварийном
возобновлении, межпроцессная конкуренция 8 SQLite соединений, проверка
ложных подписей и несовпадающих digest, инъекция SQL-отказа между W4 и
остановкой выдачи, end-to-end W3→inbox W4→receipt→issuer stop.

**Не реализовано:** этот учёт действует только для одного владельца с **общей
локальной SQLite БД**. Не доказан глобальный лимит K между независимыми
офлайновыми владельцами, не проверены настоящие Bluetooth, handoff/custody ACK,
анонимный приватный PRoPHET, криптографическая невозможность повторного
копирования злонамеренным устройством и стойкость к откату снимка диска.
Успешные тесты SQLite-ошибки не равно выключению питания/fsync-fault.
Это лабораторная цепь WOW, **не** установленный мессенджер Akula.

## Проверки

cargo test --test multipath_w5
cargo test --all-targets
cargo clippy --all-targets -- -D warnings

Существующая CI матрица также проверяет W4 ENOSPC, W5 disk и W6 QUIC loopback.
Следующее решение — токенизованный crash-safe handoff активной копии между
**независимыми** БД и приватная ограниченная таблица прогнозов адресата,
затем испытание двух реально отдельных машин с Roha/QUIC.
