# WOW CUSTODIAN P0-6 — проверка идентичностей двух узлов перед физическим испытанием

**Статус:** лабораторный криптографический preflight, не production. Зависит от PR #94, #93, #89, #88, #87. Источник требований: [WOW-CUSTODIAN-05](https://app.notion.com/p/40232a84beec81ddbc82c9748d7c704a), разделы 5, 7 и 9.

## Цель и принцип

До запуска двух физических серверов независимо закрепить идентичности C1 и C2 и не перепутать **две действительные криптографические подписи** с **доказательством двух независимых операторов / площадок**.

В `src/custodian_two_host_preflight.rs` реализованы:
- Внешняя 32-байтная непредсказуемая challenge от проверяющего (из CSPRNG) с ограниченным окном ≤10 минут; challenge нельзя переиспользовать.
- Каждый заявленный хост подписывает канонический контекст **двумя разными ключами**: отдельным W3 service Ed25519 и отдельно закреплённым операторским Ed25519. У подписей разные домены.
- В контексте фиксируются service_id, epoch, **заявленный** TLS EndpointId, operator_id, **заявленный** failure-domain, время и TTL. MessageId, ciphertext, ключ B, точный маршрут, список контактов и W3-digest не передаются.
- Проверка выполняется против **локально заранее закреплённых** service/operator ключей; подписи не выбирают собственные trust root. Также проверяются случайная challenge, свежесть, отзыв epoch, совпадение ожидаемых утверждений, повторы service pubkey / operator pubkey / TLS EndpointId и одинаковые домены.
- Результат `PreflightReport` всегда содержит `Independence::RequiresOutOfBandVerification` и `permits_automatic_store_or_suspension=false`. Отдельные ключи и идентификаторы не доказывают отдельные физические машины, управленцев, юрисдикции или настоящую доставку.

## Что требуется перед настоящим P0-7

1. Две управляемые **разными реальными операторами** машины или VPS (подтверждать организационную независимость отдельно), разные провайдеры/домены отказа и исключение общей владельческой панели. Проверить, что это действительно два хоста, а не два процесса одного раннера, и зафиксировать вывод человека.
2. На C1 и C2 использовать **локальные защищённые** приватные service- и operator-ключи с независимым закреплением публичных корней у проверяющего. Не класть ключи/nonce/witness private data в GitHub, Actions logs, CI variables с широким доступом, Notion или публичный MapShard.
3. Проверяющий самостоятельно создаёт challenge из системного CSPRNG, удостоверяется в времени и подтверждает точный EndpointId **на реальном QUIC/TLS-сеансе**; подписанное утверждение EndpointId без сетевого наблюдения недостаточно.
4. Выполнить P0-5 точный W7 AUDIT исключительно по отдельному signed AUDIT-grant, не по W5/W6 WRITE-only RelayGrant. Политика issuer и отзыв должны быть проверены на СЕРВЕРЕ и клиенте; STAYA/W6 grant production пока не реализован. **Текущий W7-rogue-custodian жёстко привязан к loopback и тестовым ключам: не разворачивать его на публичном VPS.**
5. На синтетическом W3 повторить honest / corrupt / delete / censor / timeout / dropped-ACK / revoked issuer / stolen token / wrong TLS peer / host crash / policy rollback / NAT/partition. Записывать точные W4 отдельно от успешных W7 и W8 (квитанция C не W4).
6. Собрать: private challenge transcript fingerprint, ответные ключи/epochs, реально увиденные QUIC EndpointIds, идентификаторы внешних подтверждений независимости операторов, влияние на W4/доступность/байты/потери/время, ложные обвинения. Не публиковать глобально адреса, message IDs и приватные operation aliases.

## Заявления, которых нельзя делать

- **«Два ключа» не равно «две физические машины».** Один участник может подписать за C1, C2 и обе заявленные площадки.
- **«Два провайдера/IP/ASN» не равно «две независимые организации».** Допускаются коррелированные отказы.
- **«W7 exact bytes» не равно «устойчивая сохранность» или «доставка B (W4)».**
- **«Локально подтвердили криптографию» не равно «узел получает право STORE/FETCH»**.
- Результат не дает права автоматически заморозить новые STORE, снять K3, изменить маршрутизацию, наложить глобальную санкцию или удалить прежний W3.

```bash
cargo test --all-targets
cargo clippy --all-targets -- -D warnings
cargo test --features iroh-transport --all-targets
cargo clippy --features iroh-transport --all-targets -- -D warnings
```

В Rust тестах `tests/custodian_two_host_preflight.rs` проверяются: подделка любой из подписей, старый run nonce, будущее время, истечение, неверный endpoint/epoch/operator, отозванный ключ, повтор одного service/operator/TLS ключа, совпадающий claimed failure domain. **Эти тесты работают на одном CI-host и НЕ являются P0-7 физической приёмкой.**

**Необходимый следующий результат:** отдельный ограниченный межхостовой runner с производственно-похожей политикой разрешений и минимальными сетевыми данными, плюс фактический отчёт двух независимых площадок. Пока этого нет, статус физической приёмки: **NOT TESTED**.
