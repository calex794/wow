# WOW EXP-019 — закрытая обратная W4 через недоверенные кастодианы

**Цель:** закрыть выявленную [WOW-THEORY-01](https://app.notion.com/p/40132a84beec81adaefef1ed747f996b) утечку `recipient_id` и `message_id` в публичной квитанции W4. Невозможно заставить недоверенного кастодиана хранить неизменённый код; он видит только непрозрачный шифрованный конверт и не получает ключ отправителя.

## Реализованный контракт

1. Отправитель А отдельно создаёт X25519/HPKE пару ключей **для обратной квитанции**. Публичный ключ и уникальная на каждое письмо 16-байтная `return_tag` должны попасть к B через ранее авторизованное приватное приглашение. `return_tag` — публичная подсказка маршрута, **не** разрешение читать/писать чужой ящик, не то же самое, что W3 `route_token`.
2. B получает настоящие W3 v3 HPKE/Ed25519 байты, аутентифицирует отправителя, атомарно пишет в свою SQLite и выдаёт **сохранённую исходную подписанную W4**. При повторе после рестарта B возвращает **ту же подпись**, не придумывает новую квитанцию.
3. После фиксации входящего B отдельно шифрует **точные подписанные W4-байты** для HPKE публичного ключа A. HPKE использует отдельный домен `Akula/WOW/private-recipient-W4/HPKE-v1` и AAD `[version,return_tag]`; в открытом заголовке **нет** `recipient_id`, `message_id`, digest или подписи.
4. Relay/C видит один фиксированный по длине конверт (202 байта в текущем формате W4), может сохранить/переслать его по `return_tag`, но не расшифровать. В реальной службе потребуются отдельные разрешения хранения и чтения, ограниченная TTL, фильтрация спама, устойчивые очереди и защита от связывания метаданных.
5. A независимо проверяет `return_tag`, собственный срок приглашения, HPKE, **Ed25519 по реестру получателей** и неизменный BLAKE3 исходного W3 в собственном журнале. Только `open_verify_and_apply` изменяет `Delivery` и останавливает multipath K. Вредоносный C не может своей подписью `CustodianStored` заменить W4.

## Что проверяется

- `src/private_return_w4.rs`: входная проверка строгой длины/версии и типа, изолированный HPKE, проверка доверенного recipient signing key; никаких downgrade к публичной W4.
- `tests/private_return_w4.rs`: создание подписанной W4 после фактического приёма W3, отсылка скрытой квитанции, реальный journal stop, дубль после перезагрузки, чужой HPKE key, подмена маршрута/AAD/AEAD, поддельная подпись кастодиана, несовпадение digest, истёкший инвайт/отзыв ключа, повреждённая оболочка.
- `tests/private_return_w4_quic.rs`: настоящее Roha/noq QUIC/TLS по loopback B → посредник → A, у посредника отдельная SQLite с **только закрытым ответом**. Посторонний TLS EndpointId, даже знающий `read_cap`, не получает W4. Клиент A получает только исходный зашифрованный ответ, проверяет и закрывает журнал.

## Ограничения

- Это **криптографический протокол + лабораторный сетевой маршрут**, не публичная автономная обратная почтовая служба. Не реализованы долговременная доставка W4 между физическими машинами, публикация/обновление приглашения в Node, регулярный сетевой опрос и GC.
- Открытый `return_tag` может коррелировать повторы, IP/время/объём пакета видны наблюдателю; нет доказательства анонимности против глобального наблюдателя. Для каждного письма нужен случайный независимый токен. HPKE не скрывает IP участников.
- Эпоха ключа/отзыв строго проверяются текущим TrustRegistry; потерянное или истёкшее приглашение может задержать обратный ACK. Не делать автоматический переход к открытому W4.
- Неизменяемость программ C, физическое число копий W3 и распределённый K3 **не решаются** этим опытом. Следующая независимая работа — [WOW #67](https://github.com/calex794/wow/issues/67).
- Все endpoint в CI находятся на **одном** GitHub runner, не двух физических ПК. Ни один тест не поднимает QUIC порт за пределами `127.0.0.1`.
