# WOW — первое письмо между двумя ПК через SSH без общей локальной сети

Дата: 23 октября 2026. Отдельный испытательный инструмент для <mention url="https://app.notion.com/p/40032a84beec81349bafc1ecd765dd58" /> (E2E-01). Исходный [LABO PR №26](https://github.com/calex794/labo/pull/26) и [WOW PR №80](https://github.com/calex794/wow/pull/80) остаются независимыми лабораторными проверками; данный сценарий не заменяет Roha/noq.

## Что делает инструмент

[`w4_tunnel_lab.rs`](../src/bin/w4_tunnel_lab.rs) работает в одном двоичном файле, **но процессы запускаются на разных компьютерах**. Взаимное доверие задаётся вручную, через отдельный проверенный канал: адресат предоставляет открытое приглашение (открытый Ed25519-ключ, открытый HPKE-ключ, случайный маршрутный токен), отправитель предоставляет собственный открытый ключ Ed25519. Секретные ключи не передаются.

- **ПК Б (получатель):** слушает **только 127.0.0.1**, имеет собственный SQLite и независимо сохранённые ключи. Признаёт только подписанный, зашифрованный W3 v3 от заранее внесённого отправителя. После проверки обязательного маршрутного токена пишет в SQLite и формирует настоящую подписанную W4 в той же транзакции. Только после записи возвращает HPKE-зашифрованную W4.
- **ПК А (отправитель):** хранит отдельные секреты, исходящий SQLite и оригинальные байты W3. Бюджет копий локально K=1. После проверки подлинности W4 адресата и BLAKE3 точного W3 переводит журнал в `Recipient`. При обрыве ответного канала сохраняет `Queued` и позволяет повторно отправить **те же байты W3** по `resend`.
- Команда `serve-drop-ack` внедряет отказ после COMMIT у адресата, до отправки W4. Повтор `resend` должен вернуть уже сохранённую W4, не создавая второе принятие.
- Доступ извне идёт **через два отдельные SSH-соединения до вашего VPS**. На компьютерах **нет публичного прослушивающего порта приложения**, общая локальная сеть не требуется. У VPS уже должен быть SSH-доступ; настройки ключей пользователей SSH и проверка отпечатков хоста обязательны.
- Исходный пакет не содержит в открытом виде постоянных идентификаторов адресата/отправителя. Обратная W4 зашифрована. IP узлов, SSH-сервер и время могут раскрывать сетевые связи: полная анонимность не заявляется.

## Готовый двоичный файл для Linux без ручной сборки

[GitHub Actions: W4 two-host test package](https://github.com/calex794/wow/actions/workflows/w4-two-host-package.yml) выпускает **временный лабораторный набор для Linux x86_64**. Его результат прикреплён к успешному запуску workflow: `wow-w4-two-host-linux-x86_64-<git-sha>`. В составе один исполняемый файл, сценарий SSH, инструкция и контрольные суммы. Первая сборка ориентирована на Ubuntu 24.04; для других дистрибутивов ABI-совместимость не проверялась.

Скачать ZIP из GitHub Actions, распаковать и выполнить:

```sh
sha256sum -c wow-w4-two-host-linux-x86_64.tar.gz.sha256
tar -xzf wow-w4-two-host-linux-x86_64.tar.gz
cd wow-w4-two-host-linux-x86_64
sha256sum -c SHA256SUMS
./w4_tunnel_lab --help  # здесь ожидается отказ с подсказкой команд
```

В `SOURCE_COMMIT` записан точный Git SHA использованного кода. Его надо сверить с GitHub Actions и сравнить на двух компьютерах. **Не переносите секретные файлы из архива или с другого ПК:** архив должен содержать только бинарный файл, исходную инструкцию, сценарий SSH и контрольные суммы.

## Рекомендуемый безопасный SSH-канал: закрытый Unix-сокет на VPS

Вместо предложенного ниже ручного `-R 127.0.0.1:42044` можно использовать [проверенный сценарий `ssh_tunnel.sh`](../scripts/w4-two-host/ssh_tunnel.sh). Он создаёт на VPS **не TCP-порт**, а закрытый Unix-сокет `$HOME/.ssh/wow-e2e/w4-labo.sock` в каталоге с режимом `0700`. Оба компьютера должны входить **под одной специально выделенной учётной записью SSH на VPS**, чтобы им был доступен этот сокет; реальные секреты W3/W4 остаются на самих ПК.

На **ПК Б** после `serve-once ... 127.0.0.1:42042` в другом терминале:

```sh
sh ssh_tunnel.sh receiver operator@vps.example
```

На **ПК А** в своём терминале:

```sh
sh ssh_tunnel.sh sender operator@vps.example
```

Затем отправлять на `127.0.0.1:42043`, как ниже. Важные свойства:

- Оба ПК делают только **исходящий SSH**, поэтому LAN, VPN и проброс входящих портов на роутере не нужны.
- На VPS должен быть `AllowStreamLocalForwarding yes`, а на обеих машинах должен быть OpenSSH, уже проверенный `known_hosts` и отдельный ключ входа на VPS. Сценарий требует `StrictHostKeyChecking=yes`, `BatchMode=yes` и `ExitOnForwardFailure=yes`, не принимает новый отпечаток хоста автоматически.
- Нельзя доверять самому VPS как получателю письма — он только транспортирует байты. При компрометации VPS соединение можно прервать, но успешная W4 всё равно требует подписи конечного адресата.
- Если соединение SSH оборвалось или Unix-сокет остался после отказа VPS, его нужно очистить в **своём защищённом каталоге**; никогда не удаляйте произвольные пути, полученные по сети.
- Можно передать одинаковый `WOW_E2E_SESSION=lab01` двум сценариям, чтобы иметь несколько отдельных опытов. Используйте только буквы, цифры, `_`, `-`, длина до 24 символов.

Ниже оставлены ручные команды с двумя TCP-пробросами как запасной вариант. Для основного опыта предпочесть **закрытый Unix-сокет**, поскольку настройки `GatewayPorts` удалённого SSH-сервера способны неожиданно расширять доступ к TCP-прослушиванию. <Link url="https://man.openbsd.org/ssh.1" title="Синтаксис перенаправления Unix-сокетов в OpenSSH"/>.

## Сборка (первая версия: Linux/macOS)

```bash
cargo build --release --bin w4_tunnel_lab
```

При запуске программу нужно брать из **одного проверенного коммита** на обоих ПК; не смешивать версии. Бинарный файл: `target/release/w4_tunnel_lab`.

**ПК А — первый терминал, настройка:**

```bash
./target/release/w4_tunnel_lab init-sender sender.keys
# Скопировать только значение SENDER_VERIFY=... на ПК Б по проверенному каналу.
```

**ПК Б — первый терминал, настройка:**

```bash
./target/release/w4_tunnel_lab init-recipient recipient.keys
# Скопировать только значение RECIPIENT_INVITE=... на ПК А по проверенному каналу.
```

Ключи `sender.keys` и `recipient.keys` автоматически создаются владельцу с правами `0600` и никогда не должны передаваться между устройствами. Эти файлы открывать обычным пользователям запрещено. На Windows эта первая версия отказывает до внедрения безопасных ограничений доступа к секретам в NTFS.

**ПК Б — второй терминал, запуск на localhost:**

```bash
./target/release/w4_tunnel_lab serve-once recipient.keys recipient.sqlite \
  'СЮДА_SENDER_VERIFY_С_ПК_A' 127.0.0.1:42042
```

Команда печатает `READY`. Каждый запуск обслуживает только **одно подключение**. Для повтора требуется снова выполнить `serve-once` с тем же `recipient.keys` и `recipient.sqlite`.

**ПК Б — третий терминал, исходящий SSH к общему VPS:**

```bash
ssh -o ExitOnForwardFailure=yes -N \
  -R 127.0.0.1:42044:127.0.0.1:42042 operator@vps.example
```

**ПК А — второй терминал, исходящий SSH к тому же VPS:**

```bash
ssh -o ExitOnForwardFailure=yes -N \
  -L 127.0.0.1:42043:127.0.0.1:42044 operator@vps.example
```

VPS должен разрешать указанные SSH-перенаправления портов; обе команды используют уже доверенные SSH-ключи и проверенные host keys. Внешние порты 42042–42044 **не открывать**. Для более строгой изоляции использовать отдельный учётный профиль на VPS с ограничениями перенаправлений SSH.

**ПК А — третий терминал:**

```bash
./target/release/w4_tunnel_lab send-new sender.keys sender.sqlite \
  'СЮДА_RECIPIENT_INVITE_С_ПК_B' 127.0.0.1:42043 \
  "$(printf '%01024d' 0)"
```

На ПК А ожидаем строки `MESSAGE_ID=...`, `RECIPIENT_CONFIRMED ...`. На ПК Б — `RECIPIENT_COMMITTED ... new` и `W4_SENT ...`. При разрыве после `MESSAGE_ID` тот же пакет повторяется:

```bash
./target/release/w4_tunnel_lab resend sender.keys sender.sqlite \
  'СЮДА_RECIPIENT_INVITE_С_ПК_B' 127.0.0.1:42043 \
  'СЮДА_MESSAGE_ID_ИЗ_ПРЕДЫДУЩЕГО_ВЫВОДА'
```

Для проверки потерянного ACK: на ПК Б сначала `serve-drop-ack` вместо `serve-once`, первый вызов на А должен **завершиться ошибкой и оставить Queued**; затем запустить `serve-once` на Б и `resend` на А, после чего он получит настоящий сохранённый W4.

## Что входит в доказательство

- Два **реально отдельных компьютера**, реальные разные файлы SQLite и независимые процессы, TCP через два SSH-соединения без LAN.
- Настоящий W3 v3 Blue, Ed25519 подпись конечного адресата, HPKE обратная W4, BLAKE3 исходного ciphertext; секреты хранятся локально.
- Нельзя считать сохранение посредником подтверждением получения.
- По журналу: отдельно фиксируются SHA коммитов, `MESSAGE_ID`, время, успешность/отказ, имя тестируемой ОС/версии, хэш исходного W3 и число байтов. Не публиковать приватные ключи или содержимое пользовательских писем.

**До реального запуска на двух ПК** это только готовый код и локальные испытания. Если SSH-сервер не настроен и второго компьютера нет, **результат E2E-01 остаётся незавершённым**.

## Жёсткие ограничения

- Это экспериментальный узкий канал K=1 **через SSH**, **не Roha/noq/UDP**, **не LABO-контактные маршруты**, не Bluetooth и не мессенджер Akula.
- Нет выдачи и отзыва постоянных полномочий устройств для продукта, межсистемной политики и безопасности от откачки ключей, защиты метаданных сетевого наблюдателя, отправки между обрывами вне действующего срока W3 и повторов без заранее установленного туннеля.
- Запуск между двумя ПК только на тестовых данных, не для чувствительной переписки.
- Важный запрет: **не запускать приложение на публичном TCP/QUIC-порту**. Публичный Roha/noq требует принятой защиты до `Incoming` и отдельной проверки.
- Linux/macOS — пока единственная поддерживаемая ОС для сохранения файлов секретов. Для Windows 10/7 нужна отдельная реализация локально защищённых ключей без ослабления прав.

## Критерии завершения

1. Rust `cargo test --all-targets` + строгий Clippy + тесты независимых процессов PASS.
2. Два независимых устройства реально отправили одно испытательное письмо 1 КиБ в одном установленном экземпляре приложения, восстановили оборванную W4; сняты хэши кода, исходов и SQLite.
3. Проверено, что на сетевых интерфейсах приложения нет публично доступных портов.
4. Для пользовательской Akula отдельно повторены эти критерии на реальном Roha/noq и доверенном реестре устройств. Пока этот шаг не завершён, не считать E2E-01 завершённым продуктовым сценарием.
