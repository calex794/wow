# WOW EXP-021 — независимый свидетель двойной выдачи C-слота

**Цель:** исполнить следующий эксперимент после [WOW EXP-020](https://app.notion.com/p/40132a84beec8149a338f94610c8034c) и [WOW #67](https://github.com/calex794/wow/issues/67). В W8 злоумышленный владелец ключа может подписать два `CustodyOffer` для одного слота, обойдя собственную SQLite: оба независимых C примут такие предложения. **Невозможно запретить чужому коду создавать подписи.** Задача W9 — обнаружить **встретившиеся** конфликтующие подписанные предложения и сохранить проверяемое свидетельство.

## 1. Граница доверия

- **Issuer W8:** источник псевдонимного права хранения. Его подпись гарантирует авторство предложения, но не честность программы.
- **Witness W9:** независимый добровольный наблюдатель. У него собственная SQLite (WAL+FULL) и Ed25519-ключ. Он проверяет подпись каждого предоставленного W8 предложения и хранит исходные подписанные оферты **локально**, без права подписи конечной W4 или чтения HPKE-тела письма.
- **Checkpoint:** подписанное witness утверждение, что свидетель *первым увидел предложение* либо обнаружил *конфликт*, привязанное к конкретному шагу цепочки.
- **Honest receiver:** может дополнительно требовать подтверждённый `FirstSeen` перед вызовом `PeerCustodyStore::accept`. У такой проверки пока **нет гарантии свежести**: после выдачи `FirstSeen` источник может подписать вторую ветку. Злонамеренный C может вообще не выполнять проверку.
- **Client gossip:** сравнение **достоверно подписанных** контрольных точек witness позволяет обнаружить расхождение при одинаковом номере последовательности или несовместимые соседние контрольные точки. Без обмена наблюдениями свидетеля невозможно вынудить раскрыть другую историю.

## 2. Rust API и сетевая приватность

Новый модуль `src/custody_witness_w9.rs`:

- `WitnessStore::open`: закрепляет `witness_id/epoch` за SQLite; хранилище ограничено максимум 1024 записями на лабораторию. SQLite `WAL + FULL`. Нельзя случайно открыть файл под другой свидетельский ID.
- `WitnessStore::observe`: проверяет подпись W8 через внешне закреплённый `TrustRegistry`, затем атомарно записывает событие/предыдущее состояние/подписанный checkpoint **перед ответом**.
- `WitnessObservation::FirstSeen`: первый подписанный офер для `slot_commitment=BLAKE3(domain || pseudonymous_source_id || random_slot_alias)`. Повтор **точно тех же** байтов после рестарта возвращает прежний чекпойнт.
- `WitnessObservation::Conflict`: две разных корректных подписи **одного issuer** для **одного slot_alias**, сохранённые исходные signed offer, первый checkpoint и подписанная заметка о конфликте. После обнаружения обе оферты, включая первую, больше не возвращаются как новый `FirstSeen`. Третья выдача не расширяет хранилище: ограничение DoS.
- `verify_fork`: независимо проверяет обе подписи источника, совпадение issuer+slot_alias, различие оригинальных signed offers и привязку двух свидетельских подпечатков. **Доказано только двойное подписание в наблюдаемом наборе**, не существование/количество физических копий.
- `verify_checkpoint`, `compare_checkpoints`: подпись Ed25519, hash chain по BLAKE3, `Same`, `Adjacent`, `Equivocation`, `RollbackSuspected`, `MissingHistory`. При наличии пробела цепочка **не считается автоматически проверенной**. Подозрение на откат может означать старую информацию, не доказанное злодеяние.
- `accept_witnessed`: опциональный интерфейс для *честного* C, требующий точно подписанный свидетельский `FirstSeen` на тот же offer, прежде чем вызвать независимый `PeerCustodyStore::accept`. Исторический `FirstSeen` — **не** гарантия отсутствия поздней вилки; клиент должен дополнительно запросить актуальную картину при высоких требованиях.

**Данные witness хранятся приватно.** Исходная signed оферта содержит псевдоним peer/issuer и digest ciphertext. Её НЕ публикуем в открытом глобальном журнале. Наружный witness checkpoint имеет только подписанные domain-separated hashes, sequence, verdict и собственную идентичность свидетеля. Сами хеши могут коррелировать повторные предложения одного слота, а предъявление raw fork evidence раскрывает два псевдонима целей. Требуется ограничение доступа, TTL и отдельный анализ метаданных перед общедоступным развёртыванием.

## 3. Проверка на реальном коде

`tests/custody_witness_w9.rs`:

1. Подлинное W8 предложение, подпись свидетеля, повтор и перезапуск его отдельной SQLite.
2. Два злонамеренно подписанных предложения для **одного** слота, которые в W8 действительно принимаются на X/Y. Свидетель обнаруживает вилку, сохраняет два исходника, выдаёт проверяемое свидетельство и не «лечит» физическую двойную выдачу.
3. Чужой witness-key и подмена подписи issuer не могут загрязнить лог.
4. Опциональный receiver-gate отвергает неверный WitnessId, чужое предложение и повреждённый checkpoint, допускает точно подтверждённое предложение; подпись PeerAccepted не превращается в W4.
5. Два отдельных файла SQLite с **одним злонамеренным WitnessId/ключом** могут подписать два `FirstSeen` с **одинаковым номером и разной головой**; это доказуемо при обмене двумя receipts.
6. Последовательные подписанные точки проверяются соседним звеном; gap и регрессия не считаются подтверждённой непрерывной историей.
7. Подмена пары исходных signed offers или свидетельской подписи вызывает отказ.
8. Отзыв ключа witness приводит к отказу текущего реестра проверять его чекпойнты.
9. **Исторический first-seen остаётся криптографически правильным после поздней вилки.** Это обязательный контрпример против ложного «раз навсегда одобрено».

## 4. Почему это не CT и не глобальный консенсус

Работа вдохновлена [RFC 9162 Certificate Transparency](https://www.rfc-editor.org/rfc/rfc9162.html) — idea signed checkpoints + monitoring, equivocation, gossip — **но W9 не является реализацией RFC 9162**. Вместо Merkle tree с inclusion/consistency proofs применена простая линейная цепочка последовательных свидетельств, которую возможно проверить только при наличии **соседних** подписанных сообщений (или иного доверенного способа сверки промежутка). При offline-глобальном рассогласовании ни witness, ни алгоритм не дают запрета вторых физических копий.

Опциональные несколько независимых свидетелей могут увеличить вероятность обнаружения, но не являются доказательством независимости их владельцев/дисков. Для более сильной модели нужны: доказательства включения/непрерывности, независимый checkpoint pinning, приватная сеть обмена и политика доверия quorum; ценой станет доступность без сети.

## 5. Приёмка, ограничения и следующий этап

Команды: `cargo test --test custody_witness_w9`; `cargo clippy --all-targets -- -D warnings`. Используем имеющийся CI, **не** добавляем пятый тяжёлый job.

**Что не сделали:** реальное многоузловое QUIC-взаимодействие с приватным свидетелем, физически разные операторские машины, аппаратный anti-rollback, глобальную византийскую K3, серверную политику публичного журнала или настоящий консенсус. Оставить [WOW #67](https://github.com/calex794/wow/issues/67) открытой; следующий практический опыт — приватная отправка подписанных оферт в witness по отдельной TLS-сессии, локальный checkpoint pinning/gossip, а затем [WOW #69](https://github.com/calex794/wow/issues/69) на двух физических хостах с реальным питанием/задержками.
