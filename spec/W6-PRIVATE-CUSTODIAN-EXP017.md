# EXP-017 — настоящий приватный W3 v3, Ed25519 и Roha/noq между двумя хранителями

**Статус:** эксперимент, НЕ готовая открытая сеть, не перенос прав между недоверенными SQLite и НЕ проверка двух физических компьютеров.

## Что именно реализовано

- WOW закрепляет Blue на ревизии `6728da03a49fb6c7da317e6021de65f5a242816c`, которая содержит W3 v2 и приватный W3 v3. Старый W3 v2 продолжает работать для явно выбранных прежних проверок, без автоматического понижения W3 v3.
- `src/private_route_w3.rs` — тонкий адаптер к Blue `seal_private_v3/open_private_v3`: X25519/HPKE + COSE Ed25519, постоянные ID внутри закрытого содержания, снаружи только 16-байтная случайная маршрутная метка и неаутентифицированная подсказка. Токен не является правом на чужую почту или Vault.
- `src/custody_receipt_w6.rs` — отдельное от W4 свидетельство `CustodianStored`, подписанное Ed25519, привязанное к точному BLAKE3 шифротекста, `slot_id`, `custodian_id`, `message_id`, эпохе и сроку. Указанный подписант проверяется по внешнему реестру доверия; чтение/приём чужой почты регулируется отдельно. **Подпись сама не доказывает наличие данных у злонамеренного хранителя**.
- `Journal::accept_private_authenticated_and_queue_receipt` — после аутентификации W3 v3 и проверки получателя атомарно записывает в SQLite dedup и настоящую **подписанную Ed25519 W4 конечного адресата**. Дубли возвращают сохранённые байты той же W4, а не подписывают новую квитанцию. **Публичная W4 пока содержит открытые ID**: нельзя пересылать её через недоверенных посредников, пока не сделана отдельная закрытая оболочка обратного пути.
- `tests/private_custodian_w3.rs` — реальные криптографические W3 v3 + W4, два независимых SQLite, перезапуск читателя, проверки подделки, отзыва, неверного приглашения и раздельности `CustodianStored`/W4.
- `tests/iroh_authenticated_w6.rs` — новый тест использует **два разных реальных Roha/noq EndpointId**, отдельные операторами подписанные правила допуска, две разные SQLite и реальную QUIC/TLS-сессию от личного P к общему Y. Передаёт ТОТ ЖЕ ciphertext, затем B расшифровывает/проверяет W3 и подписывает W4.

## Основная трасса теста

1. A шифрует одно письмо для B ровно один раз: W3 v3 с Ed25519 sender.
2. QUIC/TLS от доверенного A к личному P; P при наличии подписанного точного `RelayGrant` и операторской привязки EndpointId сохраняет W3 в своей SQLite. Возвращаемый статус означает **только** `MailboxStored`.
3. После завершения клиентской передачи P устанавливает новую TLS-сессию на отдельный общий Y. Y отдельно привязывает физическую идентичность сессии к разрешённой роли P с подписанным операторским обновлением и внешним контрольным отпечатком политики.
4. Y проверяет точный `RelayGrant`, сохраняет неизменные байты во второй SQLite, затем новый локальный читатель забирает их и проверяет BLAKE3.
5. Y выдаёт свидетельство собственного хранения `CustodianStored` (отдельный Ed25519 домен), не финальную W4.
6. Только B с HPKE-секретом и доверенным отправителем открывает W3, записывает сообщение в свой SQLite и формирует настоящую подписанную W4 после успешного коммита. Оригинальный отправитель проверяет подпись и digest, затем помечает свою запись окончательно принятой.

## Что остаётся открытым

- **Нет физических двух серверов:** оба EndpointId в лаборатории живут на одном GitHub Runner и привязаны к `127.0.0.1`. Двух независимых машин или удалённой инфраструктуры этим тестом нельзя доказать.
- Отдельный Ed25519 `CustodianStored` подписывается локально ПОСЛЕ записи на диске, **не** возвращается по сети и не переносит глобальный кредит. [WOW issue #67](https://github.com/calex794/wow/issues/67) остаётся открытым; общий K3/K4 между недоверенными хранилищами тут не утверждается.
- Нет приватного обратного маршрута W4 (подписанная квитанция всё ещё содержит recipient_id/message_id открытым текстом). Задержанную W4 при реальном отказе отправителя ещё нужно реализовать.
- Нет публичного каталога общих C, распределённого приглашения, отзыва разрешения на уровне постоянного NodeStore или поддержки нескольких независимых операторов с внешним управлением ключами; ключи стенда детерминированные и только тестовые.
- Открыт сценарий физического отключения/питания после COMMIT, спам и ресурсные ограничения общедоступного кастодиана и физический BLE↔Roha-шлюз.
- Независимые реальные серверы требуют отдельного разрешённого сетевого стенда, механизма выдачи ключей и проверки двух разных машин. **Не выдавать localhost-тест за физический.**

## Точная команда проверки

- `cargo test --test private_custodian_w3`
- `cargo test --features iroh-transport --test iroh_authenticated_w6 private_w3_v3_personal_to_public_custodian_over_real_roha_quic`
- `cargo clippy --all-targets -- -D warnings`
- `cargo clippy --features iroh-transport --all-targets -- -D warnings`

Встроенный `rust.yml` по текущей политике вызывает дополнительные широкие проверки для каждого PR; не считать зелёным только один сценарий без обязательных независимых проверок.

## Следующая проверка с реальными двумя ПК

После завершения этого PR вынести настройку двух независимых Node-операторов в отдельную лабораторную исполняемую программу: параметры конечного EndpointId/адреса и доверенные ключи передаются оператором вне сетевых пакетов, приложение допускает только выбранный W3 v3 и подписанный `RelayGrant`. Запуск на **разных физических хостах** фиксирует серийные номера/узлы без публикации пользовательских секретов, локальные хеши исходного пакета, сетевой захват, durable readback после перезагрузки, сетевые потери и подлинную W4 по отдельному защищённому пути.
