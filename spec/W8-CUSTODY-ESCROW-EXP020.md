# WOW EXP-020 — один слот хранения между независимыми SQLite

**Цель:** проверить часть [WOW #67](https://github.com/calex794/wow/issues/67) на настоящих Rust/SQLite. Строго разделить **честный источник с журналом полномочий** и **недоверенных держателей байтов**, способных подделывать свою историю.

## Какой контракт добавлен

- `CustodyOffer` — подписанное Ed25519 ограниченное предложение одного ранее резервированного слота `RouteAttempt.alias`. Источник создаёт его только после `Journal::reserve_multipath` с общим бюджетом K, проверяет собственную подписанную идентичность, конкретного peer, точный BLAKE3 исходного приватного W3 v3 и срок. Внешний кадр содержит **псевдонимы источника/peer**, случайные `slot_alias/offer_id`, digest и expiry, **но не** постоянные ID конечного получателя.
- Источник держит `custody_transfer_source` **в той же SQLite**, что исходный W3 и multipath-plan. `BEGIN IMMEDIATE`, WAL+FULL, уникальная пара (recipient,message,slot_alias) и глобально уникальный `offer_id`; одно право нельзя честно подписать в пользу двух peer. Повтор того же предложения даёт те же байты.
- Целевой кастодиан имеет **свою независимую SQLite**, проверяет текущий реестр доверия и отдельную привязку ожидаемого источника и собственного ключа, срок, точный digest переданных W3, один слот и квоту. Только после записи исходного W3 и квитанции в SQLite выдаёт отдельную подписанную Ed25519 `PeerAccepted`. Повтор после нового открытия его БД возвращает **точно ту же** квитанцию.
- В источнике три важных состояния: `Pending`, `Ambiguous` (ACK потерян) и `PeerClaimed` (источник проверил подпись конкретного peer о принятии). Никакое из них **не** является `Delivery::Recipient`. `Ambiguous` не освобождает слот по тайм-ауту. Конечная подлинная W4 переводит source в `RecipientConfirmed` и останавливает multipath в одной локальной транзакции.
- **Положительная проверка двойной развилки:** если сам подписант намеренно обходит честный исходящий журнал и подписывает два разных предложения для одного слота, два независимых приёмника могут их принять. Это **ожидаемый контрпример**, не баг Ed25519. Для противодействия нужны внешние независимые checkpoints/проверка конфликтов или дополнительная доверенная инфраструктура.

## Конкретные тесты

1. Две разные SQLite source/X, один подписанный офер и сохранённые точные байты, потерянный ACK, перезапуск обеих БД, `Ambiguous`, неизменный повтор офера, прежний `PeerAccepted`, затем `PeerClaimed`. Слот не выдаётся Y.
2. Чужой peer, изменение W3, подмена тела подписанного офера и подписи принятия отвергнуты.
3. Подделка квитанции/чужой ключ не переводят журнал в финальное состояние.
4. Отозванный источник, истёкший offer и немонотонные часы отказываются безопасно.
5. Подлинная конечная W4 закрывает source + все связанные маршруты в одной SQLite; поздний PeerAccepted не возвращает кредит.
6. Две параллельные SQLite-сессии одного честного источника конкурируют за один слот и **ровно одна** сохраняет конкретное предложение.
7. **Модель недоверенного источника:** две подписи разных оферов на один слот для X/Y могут быть приняты их отдельными файлами SQLite; честный протокол это не исключает, значит нужна независимая опора доверия.

## Честные ограничения

- Это **два/три файла SQLite на одном CI Linux Runner**, не разные физические серверы. Протокол подписи работает локально в лаборатории; не добавлены сетевой QUIC-сервис передачи офера/ACK и защитный закрытый обратный маршрут для него. Передача готовых байтов через сеть — дальнейший этап.
- `PeerAccepted` подтверждает **действительную подпись узла о принятии**, не неопровержимое удержание файлов при изменённом коде. Независимый сетевой аудит W7 остаётся нужен.
- Честный логический K3 не запрещает физические копии ciphertext и не предотвращает злоумышленный fork/rollback локальной SQLite. Даже подписи двух честных PeerID не доказывают двух независимых дисков.
- Нет автоматического возврата кредитов по сроку, отсутствующему ACK или недоступности peer: это осознанная цена корректной неопределённости. Для продолжения после длительного разделения сети потребуется отдельный согласованный протокол разрешения спорного слота.
- Не считать `PeerClaimed` доставкой адресату и не подключать к Akula Vault/Sync Core/File Gate.
- Не создавать дополнительное тяжёлое задание CI. Проверять стандартные 4 jobs и новые тесты W8.
