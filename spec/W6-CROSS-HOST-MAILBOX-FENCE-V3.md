# W6 cross-host Mailbox COMMIT fence / authority protocol v3

Status: laboratory Draft PR stacked on #38. **Not production-ready.**

## Security invariant

At no moment may a trusted W6 node *durably commit* a Mailbox write
using an earlier policy checkpoint after the independent authority has
*successfully published* a signed revocation advancing that checkpoint.
Checking `anchor.current()` immediately before a write is insufficient
because the revoke CAS can run on another host between that GET and
Mailbox COMMIT.

## Authority protocol v3

ALPN: `akula-wow/w6-external-anchor-lab/3`. No v2 downgrade.

* GET (op 1) and signed operator CAS (op 2) are otherwise unchanged.
* Begin writer (op 3), finish writer (op 4): exactly
  `opcode[1] || expected_revision+digest[40] || nonce[32]` (73 bytes).
* Success: `STATUS_OK[1] || pinned_authority_id[32] || checkpoint[40]` (73 bytes).
  Other statuses are one byte; CAS/GET/WRITE responses must match the
  client's independently pinned authority ID and the expected checkpoint.
* Each accepted writer uses a fresh 256-bit CSPRNG nonce *generated by the
  caller*; it is never read from unauthenticated peer message frames.
  An exact duplicate BEGIN for the same reader/checkpoint/nonce is
  idempotent, permitting a retry after a lost response.
* The authority must authenticate the pinned **reader** TLS EndpointId for
  BEGIN and FINISH; the pinned admin TLS credential cannot acquire or release
  reader permits. FINISH requires the exact original writer, checkpoint,
  and nonce. Guesses, reused unrelated nonces, zero nonce and stale
  checkpoint are refused.

The remote SQLite database contains an exclusive `w6_writer_fence` row,
including pinned reader EndpointId, 32-byte nonce and exact checkpoint.
Its insertion/deletion is a `BEGIN IMMEDIATE`, `synchronous=FULL`
transaction on the **same SQLite database** as signed policy CAS. CAS is
always rejected with Conflict if any fence exists, irrespective of whether
the signed command is Allow or Revoke. This establishes a global
linearization order across independent local policy SQLite databases.

## Mandatory Mailbox order

1. Use a local SQLite IMMEDIATE policy transaction; verify no pending signed
   policy transition and compare the local canonical digest to the fresh
   remote authority digest.
2. Check the specific enrolled TLS peer/route permission locally; invalid
   inbound peers must never acquire a durable remote permit.
3. Only with the same authority domain ID, issue BEGIN(write fence) using
   the exact checkpoint and a fresh CSPRNG nonce. A remote CAS performed
   after GET but before BEGIN causes BEGIN to fail closed.
4. While the remote fence is held, invoke the Mailbox callback and require
   its **durable COMMIT** before returning. Keep the local policy transaction
   open until that callback returns.
5. Commit the local policy read/lock transaction; only *then* send
   FINISH(write fence) with the same nonce/checkpoint.
6. Do **not** emit a recipient ACK on an ambiguous or failed fence FINISH.
   A successful Mailbox durable COMMIT followed by a lost FINISH response
   may result in a retry; idempotent/deduplicated Mailbox delivery is required
   at the recipient layer.

**Fail-safe crash behavior:** a callback error, local COMMIT failure,
timeout, SIGKILL or lost FINISH response leaves the remote fence in HOLD
unless the authority actually committed the exact FINISH. Never
auto-release based on a clock, network drop, process restart, background
GC, or speculative rollback. This can block the entire authority from
future signed CAS and writes; the operator must reconcile the crashed
writer's actual Mailbox outcome and stop stale processes before any
manual unlock procedure is designed/approved.

## Offline revoke versus remote COMMIT

When host B holds a Mailbox fence, host A's operator-signed revoke
cannot advance the authority. A's already durable signed crash-gap
journal remains `PendingRecovery` after Conflict. Once B positively
completes its Mailbox COMMIT and FINISH, A may retry the *same signed*
CAS using PR #37's forward-only recovery; the remote authority advances.
Host B's unreplicated local SQLite policy then fails remote checkpoint
comparison and cannot obtain a new fence. Host A must not report the
revoke complete merely because its command was staged locally.

## Regression plan and limits

* Authority direct tests: caller-key enforcement, idempotent BEGIN,
  wrong nonce FINISH refusal, signed CAS refusal while fenced, stale
  checkpoint and no automatic v2 schema upgrade.
* Same-machine, separate OS authority child process: SIGKILL/restart
  retains the fence and blocks CAS until explicit FINISH.
* Two distinct *local SQLite policy files* (host A and B simulation),
  real Roha/noq QUIC, and a separate **durable SQLite Mailbox file**.
  B's COMMIT window overlaps A's revoke attempt. Revoke remains
  unpublished until B finishes; after revoke B's next write fails.
* W4/W5 ENOSPC, Rust and strict Clippy, Roha/noq pinned-fork checks all
  must pass on the final SHA in push **and** PR CI.

**Not yet proven:** physical two-host deployment; multiple independent
authorized reader TLS identities (the present laboratory policy pins one
reader and one admin; simulated hosts use the same trusted reader
credential), externally attested device receipts, recovery of an orphaned
fence after a local crash, independent authority rollback protection,
pre-handshake rate limits, malicious/compromised writer behavior,
power-failure at every byte of a local Mailbox COMMIT, and production
availability. A leaked authorized reader key/nonce can defeat the
cooperative safety assumptions; do not call this a certified distributed
transaction coordinator.
