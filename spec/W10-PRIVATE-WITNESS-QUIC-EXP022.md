# WOW EXP-022 — приватный свидетель W10 по Roha/noq и независимый checkpoint-gossip

**Назначение:** продолжение [EXP-021 (W9)](https://app.notion.com/p/40132a84beec819b95c5f3de1cdca925), [WOW #67](https://github.com/calex794/wow/issues/67). Проверить на реальной QUIC-связи, что независимый участник сохраняет подписанные W8 предложения и выдает свидетельства, а другие участники обнаруживают **split view** самого свидетеля при приватном обмене checkpoint. Это **локальный исследовательский стенд на одном GitHub Linux Runner**, а не сервис для пользователей.

## Объекты эксперимента

1. **W10 Witness server:** тестовый отдельный процесс `src/bin/w10_private_witness.rs`, доступен **только в лаборатории** с `iroh-transport` и ALPN `akula-wow/w10-private-witness-loopback/1`. Привязка к `127.0.0.1:0` и двум заранее указанным TLS EndpointId. Сторонний клиент не может предъявить оферту только по знанию route token. Сервер проверяет действительную подпись источника W8, контекст target/EndpointId и записывает checkpoint в W9 SQLite до ответа.
2. **Приватный запрос:** `SUBMIT = 0x01 || exact signed W8 offer`; `LATEST = 0x02`. Ответ `0x11 || FirstSeen checkpoint`, `0x12 || ConflictObserved checkpoint`, `0x13 || latest checkpoint` либо отказ. **Никакие сырые подписанные W8 offers или доказательства двух чужих peer ID не выдаются в сетевых ответах**. Сервер всё равно видит pseudonymous source, target, ciphertext digest и IP/время — его нужно считать доверенным по части конфиденциальности этих метаданных, но не по части правдивости поведения.
3. **W10 Pin store:** `src/witness_pin_w10.rs` — отдельная долговечная SQLite конечного узла с `WAL+FULL`, внешне заранее закреплённым `witness_id/epoch` и ключом в TrustRegistry. Первая точка — только подпись seq=1 и пустой previous head, затем только **соседние** подписанные точки; пропуск `MissingHistory`, более старое значение `Stale`. При двух корректно подписанных несовместимых версиях `Equivocation` сохраняет **обе** как доказательства и переводит pin в **Frozen** до ручного разрешения. После рестарта состояние сохраняется, `inspect` запрещено в Frozen.
4. **Независимый Gossip:** реальные QUIC/TLS-сессии peer X→Y и Y→X с другим тестовым ALPN. Клиент-получатель сверяет **подпись witness по своему доверенному реестру**, а не доверяет TLS-пиру или присланному вместе с данными ключу. QUIC-сессия в тестах закрепляет remote EndpointId. Gossip может обнаруживать split-view только **если несогласованные сообщения фактически встретились**.
5. **Намеренно злонамеренный witness:** тестовый режим `split` держит **две разные SQLite с ОДНИМ Ed25519 ключом свидетеля**. X получает seq=1 о варианте А, Y получает seq=1 о варианте Б. Оба checkpoint криптографически верны по отдельности, но взаимный peer-to-peer QUIC gossip обнаруживает и сохраняет конфликт.

## Проверки

`tests/witness_pin_w10.rs` (4 теста):
- закрепление, идемпотентность, перезапуск и отказ от несовпадающего witness/epoch;
- отклонение неопроверенного gap, stale checkpoint и rollback;
- два реальных signed seq=1 от одного ключа и разных SQLite, долговечный Frozen + fork evidence после перезапуска;
- неправильная подпись и отозванный witness-key не отравляют pin.

`tests/witness_quic_w10.rs` (2 сетевых теста):
- **honest witness process:** X и Y подписали разные W8 оферты на один слот. Изолированный свидетель по настоящему Roha/noq QUIC видит первую и вторую, сохраняет приватное доказательство; чужой EndpointId и неверное соответствие target отвергаются. X/Y получают отдельные подписанные точки; без первой точки Y не доверяет второй; после прямого peer QUIC gossip становится возможно проверить непрерывную соседнюю историю. `PeerAccepted` и W4 не подделываются.
- **split view witness process:** свидетель с настоящим ключом подписывает две разных seq=1 в двух файлах SQLite. X и Y независимо принимают их, затем отправляют друг другу по TLS. Обе конечные SQLite сохраняют вилку и блокируют дальнейшее доверие к witness даже после рестарта.

## Принципиальные ограничения и приёмка

- **Нет публичного развертывания**: ALPN/протокол лабораторные, ключи `[17;32]` и `[21;32]` фиксированные тестовые, адрес всегда loopback. Никакой перенос в пользовательский Akula Node автоматически не сделан.
- **Это не Merkle-CT, не RFC 9162, не глобальный консенсус или доступность.** W9 хранит линейную цепочку, у клиента только adjacent-проверка. Если отсутствует промежуточная точка, нельзя перескакивать через разрыв.
- **Нет физического доказательства независимых дисков**: свидетели и клиенты разные процессы/SQLite, но один GitHub runner. Никакое подписанное свидетельство не запрещает злонамеренному C копировать ciphertext, удалять письмо или игнорировать проверку.
- **Заморозка при split view не означает автоматическую разблокировку K3.** Pending/Ambiguous W8 кредит сохраняется; только действительная W4 от адресата завершает исходящий маршрут.
- **Нет гарантированной свежести** только по последовательности. Даже signed latest может быть устаревшим, если свидетелю позволено молчать. Понадобятся расписание проверки, сроки, независимые наблюдатели и безопасная процедура восстановления при потере checkpoint DB.
- **В тесте исходная signed оферта передаётся witness внутри QUIC/TLS**, поэтому не открыта стороннему пассивному наблюдателю. Сам witness знает псевдонимы и digest; глобальная анонимность не заявляется. Нельзя публиковать raw W8 offers/checkpoints в открытый каталог.

Команды:
```bash
cargo test --test witness_pin_w10
cargo test --features iroh-transport --test witness_quic_w10 -- --nocapture
cargo clippy --all-targets -- -D warnings
cargo clippy --features iroh-transport --all-targets -- -D warnings
```
Используются прежние четыре GitHub CI jobs без нового тяжёлого workflow. После зелёной приёмки [WOW #67](https://github.com/calex794/wow/issues/67) **не закрывать**, потому что злонамеренный issuer может обходить witness и выдавать не замеченные сети предложения. Далее [WOW #69](https://github.com/calex794/wow/issues/69): только на двух физических разрешённых хостах можно исследовать независимость питания, сетей и дисков, вместе с подписанными внешними checkpoint pin.
