# LABO EXP-018 → WOW: реальная криптографическая W4 на журналах отдельных модельных писем

Дата: 23 октября 2026 г. Продолжение [WOW PR №79](https://github.com/calex794/wow/pull/79) и [LABO PR №26](https://github.com/calex794/labo/pull/26). Данная работа **не** подменяет модели сетевых встреч реальной доставкой.

## Экспериментальный адаптер

[`tests/labo_exp018_trace_w4.rs`](../tests/labo_exp018_trace_w4.rs) читает сам CSV (точный состав 19 полей), проверяет причинные временные отметки, затем для каждой из 12 строк делает отдельную проверку на Rust:

1. Синтезирует новый защищённый W3 v3, используя лабораторные ключи (никаких реальных корреспондентов из SFHH/InVS). К `MessageId` привязывается только **псевдоидентификатор LABO**, не доверенная личность.
2. Сохраняет W3 в исходящий SQLite через `Journal::enqueue` и задаёт локальный бюджет K=4. **Не** превращает количество повторных записей на шлюзы в новые квоты W8.
3. Если модель **не** указывает получение адресатом, отдельный SQLite получателя **не** создаёт квитанцию, а отправитель остаётся в состоянии `Queued`, независимо от промежуточных признаков хранения.
4. Если модель задаёт событие получения, настоящий обработчик WOW проверяет подпись/шифрование W3 и одной транзакцией пишет в SQLite и генерирует **действительную Ed25519 W4**. Сразу после этого отправитель всё ещё остаётся `Queued`.
5. Если модель **не** указывает доступного обратного пути, W4 остаётся на стороне получателя; ни один промежуточный маркер не переводит отправителя в `Recipient`.
6. Если задан обратный путь, настоящий HPKE-контейнер W4 возвращается к отправителю; только после проверки подписанта, точного BLAKE3 исходного W3, срока разрешения и соответствия MessageId журнал останавливает выдачу копий. Подделка подписи шлюзом отвергается. Повтор после перезапуска идемпотентен.

Контрольная выборка: **9 модельных доставок адресату, 7 модельных возвратов подтверждения, 3 случая без доставки**. После фактической обработки Rust должно быть ровно 9 созданных подписанных квитанций у адресата и 7 подтверждённых состояний у отправителя. Эти численные результаты говорят о корректном выполнении *назначенного модели расписания*, а не о реально достигнутой доставке между людьми.

## Важное уточнение терминов хранения

Исходный CSV LABO использует имя столбца `custody_copies`. Фактически там **совокупное количество событий записи на модельные шлюзы**: копия может перемещаться повторно, поэтому встречаются значения **77 при K=4**. Это не 77 одновременно созданных копий, и этот столбец **запрещено использовать** как количество подписанных W8 слотов. Данные пригодны для временного управления проверкой W4, но их недостаточно для восстановления всех передач между независимыми хранителями. Для полного W8-воспроизведения нужен отдельный журнал событий `(message_ref, gateway_alias, event_type, tick, attempt_id)` с безопасным обезличиванием и счётом занятых слотов во времени, а не только число повторов.

## Что проверено и что не проверено

**Сейчас только код и контрольная выборка в отдельной ветке.** Признак PASS устанавливается после GitHub Actions.

- Настоящие HPKE, Ed25519, BLAKE3, SQLite WAL/COMMIT/открытие после рестарта — используются существующие проверенные модули WOW.
- Истинные контактные времена SFHH/InVS служат лишь частью математической модели LABO; Интернет, готовность шлюзов, факт получения и возврат W4 там **синтетические**.
- Этот Rust-тест не читает полный архив на CI и не моделирует все 7 680 писем. Полный CSV был отдельно проверен в LABO CI. По проверенной выборке сравниваются логика и статусы.
- Отсутствуют два физически независимых компьютера, настоящий общий сетевой путь, отключение интерфейса Bluetooth, физическая потеря носителя, недоверенные операторы, сквозная задержка и аппаратное измерение расхода.
- Проверка приватности реального пользовательского маршрута и глобального K4 при злонамеренных узлах не входит в это испытание.
